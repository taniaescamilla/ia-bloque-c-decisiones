Glosario rapido

TerminoQue significa
APIApplication Programming Interface. Una puerta de entrada que permite a un programa pedir datos o acciones a otro sistema a traves de URLs.
EndpointLa URL especifica donde la API recibe peticiones. Ejemplo: https://dev.to/api/articles es el endpoint de articulos.
RESTRepresentational State Transfer. Un estilo de arquitectura para APIs web que usa metodos HTTP (GET, POST, PUT, DELETE) y URLs para organizar las operaciones.
fetch()Funcion de JavaScript que permite hacer peticiones HTTP desde el navegador. Es como decirle al browser "ve a esta URL y traeme lo que responda."
Rate limitLimite de peticiones que puedes hacer por periodo de tiempo. Si lo excedes, el servidor responde con error 429 (Too Many Requests) y debes esperar.
API keyUna clave secreta que identifica a tu aplicacion ante el servidor. Algunos endpoints la requieren para controlar quien puede escribir datos.
Content-TypeEncabezado HTTP que indica el formato de los datos enviados. application/json significa que el body va en formato JSON.
PipelineFlujo de procesamiento donde los datos pasan por varias etapas en orden (obtener, filtrar, validar, almacenar). Cada etapa transforma o enriquece los datos.

Identificar la API y su documentacion

Antes de escribir una sola linea de codigo, necesitamos entender que API vamos a usar y por que. Para esta practica elegimos la API publica de Dev.to (plataforma de articulos para desarrolladores, construida sobre el framework open-source Forem).

Por que Dev.to y no una API dummy? Porque queremos datos reales que podamos verificar. Cada articulo que jalamos existe en dev.to con su URL, su autor y sus reacciones. Si el profesor abre el link, el articulo esta ahi.

Datos clave de la API:

ConceptoDetalle
Base URLhttps://dev.to/api/articles
Documentaciondevelopers.forem.com/api/v1
AutenticacionNo requerida para GET (lectura publica)
FormatoJSON (Content-Type: application/json)
Rate limit30 requests por 30 segundos
Metodos disponiblesGET (publico), POST/PUT/DELETE (requieren API key)
Nota sobre escritura: Para las operaciones de escritura (POST, PUT, DELETE), Dev.to requiere un API key personal. Como esta es una practica academica y no queremos exponer credenciales, usamos DummyJSON como endpoint de simulacion para esas 3 operaciones. Los GET son 100% reales contra Dev.to.

Conectar a la API con GET (lectura real)

El primer paso practico es hacer una peticion GET a la API. Esto equivale al Read en CRUD. Usamos query parameters para filtrar los resultados:

GET https://dev.to/api/articles?tag=ai&top=7&per_page=5 // Desglose de la URL: // - https://dev.to/api/articles = endpoint base (coleccion de articulos) // - ?tag=ai = query param: filtrar por tag "ai" // - &top=7 = query param: mas populares de los ultimos 7 dias // - &per_page=5 = query param: limitar a 5 resultados

Que hace cada query parameter?

ParametroTipoFuncion
tagstringFiltra articulos que tengan este tag
topintegerVentana de tiempo en dias (7 = ultima semana)
per_pageintegerCantidad maxima de resultados por pagina
Diferencia clave: Los query parameters van despues del ? y filtran una coleccion. Los path parameters van en la URL misma (ej. /articles/4559844) y apuntan a un recurso especifico. Ambos son parte fundamental del diseno REST.

La respuesta es un array de objetos JSON. Cada objeto representa un articulo con esta estructura:

// Respuesta real (extracto de 1 articulo): { "id": 4559844, "title": "20 Agentic AI Terms Every Developer Should Know", "url": "https://dev.to/sylwia-lask/20-agentic-ai-terms-...", "published_at": "2026-09-03T06:44:57Z", "reading_time_minutes": 11, "comments_count": 115, "public_reactions_count": 217, "tag_list": ["ai", "agents", "mcp", "beginners"], "user": { "name": "Sylwia Laskowska", "username": "sylwia-lask" } }

Analizar la estructura JSON de la respuesta

Cada articulo demuestra los 6 tipos de datos JSON en accion:

Tipo JSONEjemplo en la respuestaCampo
String"20 Agentic AI Terms..."title, url, published_at
Number217id, comments_count, reactions
Booleantrue / falseNo hay un campo booleano explicito en esta respuesta, pero JSON soporta valores true/false. Ejemplo: "is_published": true
Nullnullgithub_username (cuando no tiene)
Array["ai", "agents", "mcp"]tag_list
Object{"name": "Sylwia", ...}user (objeto anidado)
Objetos anidados: El campo user es un objeto dentro de otro objeto. En SQL esto requeriria una tabla separada con foreign key. En JSON (y en NoSQL/MongoDB), se almacena tal cual, embebido en el mismo documento. Este es uno de los diferenciadores principales de las bases de datos orientadas a documentos.

Definir un JSON Schema de validacion

Para asegurar que los 3 archivos del equipo tienen la misma estructura, definimos un JSON Schema (draft 2020-12) que valida:

// schema_devto_article.json (extracto) { "$schema": "https://json-schema.org/draft/2020-12/schema", "type": "object", "required": ["fuente", "endpoint", "responsable", "articulos"], "properties": { "fuente": { "const": "Dev.to API" }, // valor fijo "endpoint": { "pattern": "^GET https://dev\\.to/api/articles" }, "articulos": { "type": "array", "items": { "required": ["id", "title", "url", "tag_list", "user"], "properties": { "url": { "pattern": "^https://dev\\.to/" }, "tag_list": { "maxItems": 4 }, "ai_disclosure_level": { "enum": ["not_disclosed", "some_ai", "fully_ai"] } } } } } }
Que valida el Schema: Que fuente sea exactamente "Dev.to API" (const), que el endpoint cumpla un patron regex, que cada articulo tenga los campos requeridos, que las URLs empiecen con https://dev.to/, que tag_list no exceda 4 elementos, y que ai_disclosure_level sea uno de 3 valores permitidos (enum).

Que significa cada keyword del Schema:

KeywordQue haceEjemplo en nuestro schema
constEl campo debe tener EXACTAMENTE este valor"fuente" debe ser "Dev.to API", no otro texto
patternEl texto debe cumplir esta expresion regular (patron)Las URLs deben empezar con https://dev.to/
enumSolo se permite UNO de estos valores (lista cerrada)ai_disclosure_level: "not_disclosed", "some_ai", o "fully_ai"
requiredEstos campos DEBEN existir en el objeto (no opcionales)Cada articulo debe tener id, title, url, tag_list, user
maxItemsMaximo de elementos permitidos en un arraytag_list puede tener maximo 4 tags
minLengthEl texto debe tener al menos N caracterestitle no puede estar vacio (minLength: 1)
Nota sobre ai_disclosure_level: Este campo de Dev.to indica si el autor declaro haber usado IA para escribir el articulo. "not_disclosed" = no lo menciona, "some_ai" = uso parcial de IA, "fully_ai" = generado completamente con IA.

JSON Schema es fundamental en NoSQL porque la base de datos no impone estructura (a diferencia de SQL con CREATE TABLE). El Schema funciona como contrato entre quien escribe y quien lee los datos.

PUT vs PATCH: Tecnicamente, enviar solo algunos campos (como hacemos en el ejercicio 6) es semantica de PATCH (actualizacion parcial). PUT por definicion reemplaza el recurso completo. DummyJSON acepta ambos de la misma forma, pero en una API estricta, la diferencia importa. En la practica, muchas APIs REST usan PUT para ambos casos.
Que pasa si algo sale mal? Si envias JSON invalido en el body, el servidor responde con status 400 Bad Request. Si el recurso no existe, responde 404 Not Found. Si excedes el rate limit, responde 429 Too Many Requests. Estos codigos HTTP son estandar y significan lo mismo en cualquier API.

Conexion con NoSQL (MongoDB)

Cada archivo JSON del equipo se puede insertar directamente en una coleccion de MongoDB sin modificar la estructura:

// mongosh es la terminal interactiva de MongoDB (como psql para PostgreSQL) // 1. "use" selecciona (o crea) una base de datos use practica_json_devto // 2. "db.articulos" accede a la coleccion "articulos" (equivalente a una tabla SQL) // "insertMany" inserta un array de documentos de golpe db.articulos.insertMany([ // ...contenido de daniel_ai_articles.json ]) // 3. "find" busca documentos. Las llaves {} son el filtro. // "$gt" significa "greater than" (mayor que). Es un operador de MongoDB. // Equivalente SQL: SELECT * FROM articulos WHERE public_reactions_count > 50 db.articulos.find({ "public_reactions_count": { $gt: 50 } }) // 4. "aggregate" es el pipeline de procesamiento de MongoDB. // "$group" agrupa documentos (como GROUP BY en SQL). // "_id" define el campo por el que agrupamos (categoria). // "$sum: 1" cuenta documentos (como COUNT(*)). // "$avg" calcula el promedio (como AVG()). // Equivalente SQL: SELECT categoria, COUNT(*), AVG(reactions) FROM articulos GROUP BY categoria db.articulos.aggregate([ { $group: { "_id": "$categoria", "total": { $sum: 1 }, "avg_reactions": { $avg: "$public_reactions_count" } }} ])

Comparacion directa SQL vs MongoDB:

SQLMongoDB
SELECT * FROM articulos WHERE reactions > 50db.articulos.find({"reactions": {$gt: 50}})
INSERT INTO articulos VALUES (...)db.articulos.insertOne({...})
UPDATE articulos SET title='X' WHERE id=1db.articulos.updateOne({id:1}, {$set:{title:"X"}})
DELETE FROM articulos WHERE id=1db.articulos.deleteOne({id:1})
SELECT cat, COUNT(*), AVG(r) GROUP BY catdb.articulos.aggregate([{$group:{...}}])
SQL vs NoSQL - la diferencia clave: En SQL, el campo tag_list (array) necesitaria una tabla intermedia (articulos_tags) con foreign keys. En MongoDB, el array se almacena embebido en el documento. Lo mismo con user (objeto anidado) que en SQL seria una tabla separada con JOIN. Esta es la ventaja del modelo de documentos cuando la estructura es jerarquica.
Sobre _id en MongoDB: Cada documento recibe automaticamente un campo _id unico (tipo ObjectId). Si intentas insertar dos documentos con el mismo _id, MongoDB rechaza el segundo con un error de duplicado. Esto es equivalente a un PRIMARY KEY en SQL.

Reflexion del equipo

Que aprendimos

Trabajar con una API real en lugar de datos inventados nos obligo a entender la estructura de los datos tal como existen en produccion. Los articulos de Dev.to no tienen una estructura perfectamente uniforme: algunos tienen github_username como null, otros como string. Algunos usan ai_disclosure_level, otros no lo incluyen. Esto es exactamente lo que pasa en el mundo real, y es la razon por la que JSON Schema y las bases NoSQL son necesarios.

El ejercicio de dividir el trabajo por tags (ai, webdev, datascience) simula un pipeline real de curaduria de contenido. Cada miembro del equipo actua como un "productor" que alimenta un catalogo central. La validacion con Schema asegura que todos sigamos el mismo formato, aunque los datos vengan de consultas distintas.

La diferencia entre leer datos (GET, sin autenticacion) y escribir datos (POST/PUT/DELETE, con API key) refleja los niveles de acceso que existen en cualquier sistema real. No todo usuario puede modificar datos, y eso se controla desde la API, no desde el cliente.

Reflexiones individuales

Daniel: Al principio pensaba que todas las APIs devolvian la misma estructura, pero al comparar los 3 archivos me di cuenta de que campos como github_username vienen null en algunos articulos y como string en otros. Eso me hizo entender por que MongoDB no obliga un schema fijo y por que JSON Schema existe como capa de validacion externa.

Stephanie: Lo que mas me sorprendio fue ver que 3 de nuestros articulos aparecieron en dos categorias a la vez. No lo esperaba, pero tiene sentido: un articulo puede tener tags de "ai" y "webdev" al mismo tiempo. Eso me hizo pensar en como se disenan los filtros en una base de datos y por que los arrays son utiles en documentos NoSQL.

Abigail: Trabajar con datos de ciencia de datos fue interesante porque los articulos de mi categoria tenian muchas menos reacciones que los de AI, pero eran mas tecnicos y especializados. Entendi que la popularidad no es lo mismo que la profundidad, y que en un sistema real necesitarias diferentes metricas para filtrar contenido dependiendo de tu audiencia.
